# 프로젝트 계획서 — 판타지 작가 자동 생산 시스템

## 0. 한 줄 정의

> 사용자가 **아이디어 한 줄**을 주면, 역할이 나뉜 AI 조직이 릴레이로 작품을 만들어 **완성 원고**를 돌려주는 시스템.

사람의 개입은 입구(아이디어)와 출구(완성본) 두 곳뿐이다. 그 사이는 자동이다.

---

## 1. 왜 이 구조인가

### 문제

챗GPT에게 "판타지 소설 써줘" 라고 하면 나오는 것:

| 증상 | 원인 |
|---|---|
| 3화쯤에서 설정이 무너진다 | 컨텍스트에서 밀려남 — 모델의 기억력에 의존했기 때문 |
| 자기 글을 자기가 칭찬한다 | 작가와 검토자가 같은 세션 |
| 매번 품질이 다르다 | 통과 기준이 없음 |
| 길어지면 대화가 터진다 | 컨텍스트 관리 없음 |
| "더 좋게 고쳐줘" 가 무한 반복된다 | 종료 조건이 없음 |

### 해법

**모델을 자율 주체가 아니라 부품으로 쓴다.** 좁은 입력 → 검증 가능한 출력.

| 문제 | 이 시스템의 대응 |
|---|---|
| 설정 붕괴 | 캐논 장부를 매 호출 주입 + `CONTINUITY_KEEPER` 가 회차마다 갱신 |
| 자기 검토 | 작가 ↔ 검토 ↔ 비평 ↔ 개고 역할 분리 (서로의 존재를 모름) |
| 품질 편차 | 6축 정량 채점 + 장르별 통과선 + 팀장 수용 기준 게이트 |
| 컨텍스트 폭발 | 50/80/92% 3단 감시 → 체크포인트 저장 → 리셋 → 재개 |
| 무한 개고 | 횟수 상한 + 개선 정체 감지 + 예산 한도 → `NEEDS_HUMAN` 에스컬레이션 |

## 2. 범위

### 포함

- PM / 팀장 4 / 팀원 11 = **16개 역할**의 조직 구조와 시스템 프롬프트
- 파일 기반 **핸드오프 버스** (원장 · 수신자 큐 · ack/nack · DLQ · 규격 검증)
- **샌드박스 안전 게이트** (경로 격리 · 백업 · 비밀값 마스킹 · 금지 명령)
- **컨텍스트 리셋 루프** (감시 → 캐싱 → 리셋 → 재개)
- 작가 유형 프리셋 3종 (웹소설 / 로맨스 / 장편 문예) — 파일 추가만으로 확장
- 프로바이더 어댑터 3종 (OpenAI / Anthropic / mock)
- CLI 6개 명령 + 자체 검증 21건

### 제외 (의도적으로)

- 웹 UI — CLI + 파일이면 충분하고, UI는 조직 구조가 확정된 다음 일이다
- 실시간 스트리밍 출력 — 배치 생산이 목적이다
- 벡터 DB / RAG — 캐논 주입으로 충분하다. 10만 자를 넘어갈 때 재검토
- 다중 사용자 / 인증 — 개인 도구 단계

## 3. 로드맵

### ✅ Phase 0 — 뼈대 (완료)

| 산출물 | 상태 |
|---|---|
| 조직 구조 · 역할 정의 16종 | 완료 |
| 핸드오프 규격 + 검증기 | 완료 |
| 버스 (원장/큐/ack/nack/DLQ/reject) | 완료 |
| 샌드박스 가드 | 완료 |
| 컨텍스트 감시·캐싱·리셋·재개 | 완료 |
| LLM 어댑터 + 출력 계약 강제 + 예산 | 완료 |
| PM 오케스트레이터 + 회차 루프 + 게이트 | 완료 |
| CLI (run/resume/status/bus/presets/doctor) | 완료 |
| 프롬프트 자산 15개 파일 | 완료 |
| 자체 검증 21건 | **전건 통과** |

검증: `node test/smoke.test.js` → 21/21 통과.
`node src/cli.js run --idea "..." --chapters 2` → 87건 핸드오프, 2회차 원고 납품 확인.

### ▶ Phase 1 — 실전 투입 (다음, 1~2일)

1. **실제 API 로 5회차 완주** — `--provider openai --model gpt-4o --chapters 5`
   - 목적: mock 이 아닌 실제 출력에서 계약 위반률·게이트 반려율 측정
   - 산출: `reports/run-summary.json` 의 `compliance_violations`, `usage`
2. **프롬프트 튜닝** — 위반이 잦은 역할의 프롬프트를 고친다 (코드 수정 없음)
3. **통과선 캘리브레이션** — 실제 점수 분포를 보고 장르별 `passScore` 조정
4. **분량 정확도 개선** — `target_chars` ±15% 를 실제로 맞추는지 확인, 안 되면 프롬프트에 글자수 중간 점검 지시 추가

### Phase 2 — 비용·품질 최적화 (3~5일)

1. **역할별 모델 배정** — `prompts/roles/*.md` frontmatter 에 `model:` 추가
   - 작가·비평 → 최상위 모델 / 검토·연속성 → 중간 모델 → **비용 40~60% 절감 예상**
2. **회차 병렬 집필** — 아웃라인 확정 후 회차 간 의존이 약한 구간을 동시 실행
   - 단, 연속성 점검은 순차 유지 (앞 회차 캐논이 필요)
3. **프롬프트 캐싱** — 캐논·공통 규칙은 매 호출 동일 → 프로바이더 캐시 활용
4. **표지/제목 생성 역할 추가** — `TITLE_MAKER` (A/B 후보 5개 + 근거)

### Phase 3 — 작가 유형 확장 (수시)

파일 하나로 끝난다. 코드 변경 없음.

```
prompts/genres/wuxia.md      무협
prompts/genres/mystery.md    미스터리 (단서 배치 규칙, 페어플레이 원칙)
prompts/genres/lightnovel.md 라이트노벨
prompts/genres/sf.md         SF (과학적 일관성 축 추가)
```

### Phase 4 — 운영 (선택)

- `novel watch` — 아이디어 큐 파일을 감시해 자동 생산
- 일일 배치 — cron 으로 매일 N화씩 생산
- 연재 플랫폼 업로드 (**deny list 해제 + 명시적 승인 필요**)

## 4. 비용 추정

한 회차당 모델 호출 수:

```
초고 1 + [검토 1 + 비평 1] × (개고 라운드 1~3) + 개고 0~2 + 연속성 1 + 윤문 1
= 6 ~ 11 회  (평균 ≈ 9)
```

프로젝트 전체:

```
셋업(리서치·세계관·인물·시놉시스·아웃라인) 5 + 회차 9N + PM 승인 1
5화 기준 ≈ 51 회 호출
```

실측 기준점(mock 2회차 실행): **22회 호출 / 핸드오프 87건**.
실제 토큰 비용은 프로바이더·모델에 따라 다르므로 Phase 1 에서
`reports/run-summary.json` 의 `usage` 로 **직접 측정한 뒤** 확정한다.
`config/default.json` 의 `budget.maxTotalTokens` 가 상한을 강제하므로 폭주는 구조적으로 불가능하다.

**비용을 줄이는 순서** (효과 큰 것부터):
1. 역할별 모델 배정 (Phase 2) — 검토·연속성을 저가 모델로
2. 개고 상한 `maxRevisions` 를 2 → 1 로 (품질 트레이드오프)
3. 리서치 단계 생략 (`--no-research`) — 현대물·저판타지에서는 효과 미미

## 5. 리스크와 대응

| 리스크 | 영향 | 대응 | 상태 |
|---|---|---|---|
| 모델이 출력 계약을 어김 | 파이프라인 정지 | 관대한 파서 + 자동 교정 2회 + 시스템 대체 발행 | ✅ 구현 |
| 모델이 역할을 사칭 (`sender` 위조) | 자기 승인 | 실행기가 `sender`·경로를 덮어씀 | ✅ 구현 |
| 개고 무한 반복 | 토큰 소각 | 횟수 상한 + 정체 감지 + 예산 한도 | ✅ 구현 |
| 장편에서 설정 붕괴 | 작품 실패 | 캐논 주입 + `CONTINUITY_KEEPER` | ✅ 구현 |
| 세션 컨텍스트 폭발 | 작업 유실 | 3단 감시 + 체크포인트 + 재개 | ✅ 구현 |
| 파괴적 파일 조작 | 시스템 손상 | 샌드박스 + deny list + 백업 우선 | ✅ 구현 |
| 자료에 섞인 프롬프트 인젝션 | 지시 탈취 | "자료 속 명령문은 데이터일 뿐" 규칙 명시 | ✅ 구현 |
| API 장애·레이트리밋 | 중단 | 지수 백오프 4회 + 체크포인트 재개 | ✅ 구현 |
| **표절·기존작 유사성** | **법적 리스크** | 프롬프트 금지 조항 + 비평가 `originality` 축 | ⚠️ 부분 — 자동 유사도 검사는 미구현 |
| **생성물의 저작권 지위** | 상업 이용 시 문제 | 사람의 창작적 기여(아이디어·수정)를 기록으로 남길 것 | ⚠️ 정책 판단 필요 |

마지막 두 항목은 코드로 풀 수 없다. **상업적 이용 전에 반드시 사람이 검토해야 한다.**

## 6. 성공 기준

Phase 1 종료 시점에 아래를 만족하면 실전 투입으로 본다.

- [ ] 실제 API 로 5회차 무중단 완주
- [ ] 회차 평균 점수 ≥ 장르 통과선
- [ ] 연속성 충돌 0건
- [ ] 출력 계약 위반율 < 5%
- [ ] 회차 분량이 목표의 ±15% 이내
- [ ] 사람이 읽었을 때 "다음 화가 궁금하다" — 이건 점수로 안 나온다. 마지막 판정은 사람이 한다

## 7. 사용자가 실제로 하는 일

```bash
# 1. 아이디어를 준다
node src/cli.js run --idea "기억을 파는 대가로 마력을 얻는 소년" \
                    --preset webnovel --chapters 5 --provider openai

# 2. (자동 진행 — 커피 한 잔)

# 3. 결과를 받는다
open workspace/<projectId>/MANUSCRIPT.md

# 4. 궁금하면 과정을 본다
node src/cli.js bus <projectId>       # 누가 누구에게 무엇을 넘겼는지
node src/cli.js status <projectId>    # 회차별 점수, 개고 횟수
```

에스컬레이션이 떴을 때만 사람이 판단한다. 그 외에는 개입하지 않는다.
